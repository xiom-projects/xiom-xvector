# Compiler findings from the XVECTOR lane

Findings collected while building the xiom-xvector vector database with the
latest toolchain (owner policy: track latest; no fixed pin).

Instrument: **XIOM Compiler v0.64.0**, Windows
(`%LOCALAPPDATA%\xiom.new\bin\xiom.exe`) and Linux/WSL
(`~/.local/bin/xiom`, Ubuntu); stdlib `E:\xiom-lang\stdlib`
(`/mnt/e/xiom-lang/stdlib` in WSL) and the compiler-bundled tree; no
registry packages consumed yet (see `PACKAGE-WISHLIST-XVECTOR.md`).

Format: `| Date | Finding | Evidence | Workaround | Impact |`.
Every finding carries a minimal repro bundle under `docs/repro/`.

Reference docs read before reporting (do NOT re-run known bisections; add
delta evidence only): packages `docs/COMPILER-FINDINGS.md`,
`docs/repro/README.md`, PULSE `docs/COMPILER-FINDINGS-PULSE.md`.

## Open findings

| Date | Finding | Evidence | Workaround | Impact |
|---|---|---|---|---|
| 2026-10-08 | **XVC-C-01: calling a `&fn() -> T` parameter as `f()` emits invalid LLVM IR** (`%tmp = inttoptr i64* %tmp5 to i64 ()*` -- `inttoptr` needs an integer operand, gets a pointer) -> `clang failed with exit code 1`, `invalid cast opcode for cast from 'ptr' to 'ptr'`. The `(*f)()` spelling **compiles** but the call then uses a wrong signature (`i64 (i64)*` for a `fn() -> Int`) and **crashes at runtime** (Windows exit `-1073741819` / access violation). A `fn()` pointer in a **struct field** (`(op.f)(&x)`) is GREEN (the packages-lane `generic-fnptr` fix covers that shape; this is the *reference-parameter* call shape). | `docs/repro/xv-fnptr-call-inttoptr/probe.xi` (clang exit 1, IR at line offset: `inttoptr i64* %tmp5 to i64 ()*`); `probe_deref.xi` compiles but exits `-1073741819`; control `probe_local.xi` same crash; `probe_struct_fnfield` (packages lane) exit 0. Hit by the conformance suite: 126 test-function pointers dispatched through `fn run_one_test(fn_ptr: &fn() -> TestResult)`. | None for the call itself: **do not use `&fn()` parameters with call syntax**. Evaluate at the call site (`run_one_test(test_fn())` with a `TestResult` parameter) or use a struct-field fn pointer. The suite was rewritten to direct dispatch. | blocks all higher-order test harnesses/trampolines using `&fn()` parameters; silent runtime crash for the `(*f)()` form |
| 2026-10-08 | **XVC-C-02: a runtime `requires` violation aborts the process with exit code 0.** A contract failure prints `contract violated: requires at <line>:<col>` (stdout AND stderr) and terminates with exit 0, even when `main` would have returned a nonzero value on the same path. CI/scripts gating on the process exit code cannot see contract failures; a test suite dies silently-green. | `docs/repro/contract-trap-exit0/probe.xi`: `fn take_positive(x: Int) requires: x > 0`; `main` returns `take_positive(-5)`. Expected: continue with `-5` (exit 251) or trap nonzero. Observed: violation message, `EXIT=0` (`cmd /c ... & echo %ERRORLEVEL%`). Caught in vivo: the conformance suite called `engine_create_collection(&mut eng, 0, ...)` in a negative test -> suite aborted mid-run at 86/126 lines and reported exit 0. | Never call a contracted entry point with arguments that violate its `requires` (test the predicate instead). Scripts should also treat contract text on stdout as failure (XVPOLICY note: grep for `contract violated` in runner logs). | silent-green CI on contract violations; any harness that intentionally exercises error paths traps |
| 2026-10-08 | **XVC-C-03: W004 false positives on unit-enum `match` -- "unreachable match arm (an earlier arm already matches these values)" is emitted for EVERY arm after the first**, on matches over all-unit enums. 18+ occurrences in the conformance suite (lines 354-355, 583-588, 607, 614, 926-927, 961-962, 2299-2301, 2441...). All arms are distinct variants; `--explain W004` semantics do not apply. A real unreachable arm would be buried in the noise. | `tests/test_conformance.xi` compile log: `warning[W004]` on `match metric { Cosine, DotProduct, Euclidean }`, on the 7-arm `SegmentStateKind` map, and on 3-arm `AnnIndexKind` / `DistanceMetric` maps; no duplicate arms exist. | None needed (warning-level); do not rely on W004 to find dead arms on this pin. | warning noise hides genuine unreachable-arm diagnostics; checker treats distinct unit variants as equal patterns |
| 2026-10-08 | **XVC-C-04: a `Result[T, E]` / `Option[T]` whose payload is DIRECTLY a `Vec[non-scalar]` loses element field data at the caller**: the length survives, but struct element fields read as `0` and `Str` element fields read as address-like integers. `Result[Vec[Int], E]`, `Result[Int, E]`, `Result[Struct{Int,Float32}, E]`, direct `Vec[SR]` / direct `Vec[Str]` returns and `Option[Struct-with-Vec-field]` are all GREEN -- the broken shapes are `Result[Vec[SR], E]`, `Result[Vec[Str], E]`, `Option[Vec[SR]]`. Wrapping the Vec in a struct repairs the payload (`Result[Hits{items: Vec[SR]}, E]` -> correct). Found when `engine_search` returned `Result[Vec[SearchResult], CoreError]` and a consumer read `Ok(hits)` with every `id`/`distance` zeroed. (Regression/extension of the v0.62.2-fixed generic-fnptr ABI family -- do not fold into it; the fixed probes only cover the struct-field fn shape and scalar `Vec[U]`.) | `docs/repro/xv-result-vec-struct/probe.xi` (direct vs wrapped: `id=42` vs `id=0`); `probe_matrix.xi` (6-shape matrix: only the two `Result[Vec[non-scalar]]` rows corrupt); `probe_workaround.xi` (wrapper green, `Option[Vec[SR]]` red). Engine consumer A/B: `tests/probes/probe_vector_store.xi` search hit ids 1,2 with zero distances before the wrapper. | Wrap the Vec in a struct payload (`type SearchHits = { items: Vec[SearchResult]; }`) -- adopted by `src/engine.xi` (`SearchHits`) and mirrored in the suite (`test_search_hits_shape` is the regression guard). Unwrap when fixed. | silent wrong query results for any API returning `Result[Vec[Row]]`; exactly the shape a vector DB returns |
| 2026-10-08 | **XVC-C-05 (major): per-build nondeterministic codegen -- Float32 arithmetic on `Vec[Float32]` elements can be lowered as INTEGER arithmetic on the IEEE-754 bit patterns.** In `probe_failing.xi`, a red build's `vector_dot(p2, q)` returns double `1.13319008125164e+18` = `1063675494 x 1065353216` = `0x3F666666 x 0x3F800000` -- the f32 **bit patterns** of `0.9` and `1.0` multiplied as `Int`s; `p2.data[0]` prints as `1063675494.0` (the integer of `0x3F666666`). Green builds of the same bytes are exact. Correctness flips **per compilation**: irrelevant byte changes (a comment, the module name) and the `--sequential` flag all perturb which lowering is emitted, in BOTH directions. Smaller sibling probes importing the SAME engine module (`evidence_debug_cosine.xi`, `evidence_bisect_a/b/c.xi`) were green in every compile; the 136-check suite compiled green 5/5; a self-contained control is green. So the trigger is compilation-unit shape + emission order, not the source semantics. This is the same family as the packages-lane "nondeterministic payload-length read" note and may share the downstream cause. | Bundle `docs/repro/xv-f32-int-miscompile/`: `probe_failing.xi` (flaky), `evidence_debug_cosine.xi` + `evidence_bisect_a/b/c.xi` + `evidence_debug_search.xi` (green controls), `control_selfcontained_min.xi` (green self-contained), `linux_matrix.sh` (WSL matrix runner). Measured 2026-10-08, v0.64.0: Windows same-bytes default **1/3, 2/3 and 1/3 red** across three 3x batches (never stable); Windows `--sequential` **2/3 red then 3/3 green on earlier bytes** (not a fix); WSL Linux default **3/3 red** on earlier bytes, **3/3 green** after a comment-only change; WSL `--sequential` 3/3 red on the later bytes. Full raw-bits decode in the bundle README. | **No reliable flag workaround.** Treat a red numeric check as a build rejection: every evidence build must run its own numeric assertions (the suite/probe do); rebuild and re-verify rather than trusting a binary. `scripts/build.ps1 -Sequential` / `XVECTOR_SEQUENTIAL=1 scripts/build.sh` remain as A/B diagnostics only. | silent wrong numeric results in any production unit -- a vector DB's distance kernel is exactly this shape; needs compiler-lane localization of the int/float lowering decision (watch for a unit-hash/order dependency) |

## Notes for the compiler lane

- Re-run recipe (Windows):
  `.\scripts\build.ps1 docs\repro\xv-f32-int-miscompile\probe_failing.xi -Name pf`
  then run `out\pf.exe`; repeat 3x — expect nondeterminism on Windows.
  `-Sequential` is the A/B switch. On WSL:
  `bash scripts/build.sh docs/repro/... <name>` (set `XVECTOR_SEQUENTIAL=1` for the flag).
- The conformance suite is `tests/test_conformance.xi` (136 checks, self-contained; does not import `src/engine.xi`).
  Run: `scripts\run-suite.ps1` / `bash scripts/run-suite.sh`.
- The critical-primitive probe is `tests/probes/probe_vector_store.xi` (imports `src/engine.xi` via `xiom.toml` roots;
  exercise with `scripts\run-probe.ps1 tests\probes\probe_vector_store.xi -Sequential`).
- Bump procedure when the next archive lands: re-run all five repro bundles FIRST,
  then the suite x2 + the probe, then re-pin in `SESSION.md`.
